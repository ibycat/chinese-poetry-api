## 为什么不是"把数据打进 Worker"

Worker 打包上限看着宽松（64 MiB），但**启动必须在 1 秒内完成**。7.6 万首诗的 JSON 有 40 MB，
顶层 `import` 或 `JSON.parse` 必然突破这个上限，部署会被拒（错误码 10021）。

因此本方案：

| 部分 | 位置 | 原因 |
|---|---|---|
| 路由、随机抽取、SVG 渲染 | Worker（约 **27 KiB**） | 体积极小，冷启动几十毫秒 |
| 571,189 首语料 | Static Assets（220 MB / 4086 个文件） | 文件数上限 20,000、单文件 25 MiB，都不触碰 |
| 文档页、浏览页 | Static Assets | 由静态层直接返回，不消耗 Worker CPU |
| IP 限流 | 原生 Rate Limiting（60 次 / 60 秒） | 无状态、按机房近似计数，允许突发 |

单条分类请求通常读 **2 次子请求**（分类下标 + 诗库分片）；`n>1` 会按条数增加。
单次最多取 50 条的是全库路径，分类与多选限制为 20 条，避免触碰 50 子请求上限。

## 部署

```bash
cd cloudflare

# 1. 安装 wrangler（首次）
npm install

# 2. 从全量语料生成部署产物（约 20 秒）
python ../tools/build_cf.py

# 3. 登录（浏览器授权一次）
npx wrangler login

# 4. 部署
npx wrangler deploy
```

成功后输出形如：

```
https://chinese-poetry-api.<你的子域>.workers.dev
```

首次部署即生效。IP 限流使用 Cloudflare 原生 Rate Limiting，无需数据库、KV 或 Durable Object。

### 本地预览（不需要登录）

```bash
npx wrangler dev --port 8787
# 打开 http://127.0.0.1:8787/
```

### 绑定自定义域名

在 Cloudflare 控制台：**Workers & Pages → chinese-poetry-api → Settings → Domains & Routes → Add custom domain**。
域名需已托管在同一个 Cloudflare 账号下，证书自动签发。

## 产物结构

```
cloudflare/
├─ wrangler.jsonc
├─ src/
│  ├─ index.js          路由与随机抽取（唯一需要读的代码）
│  └─ manifest.js       生成物：分类树 + 诗库分片边界（5.3 KB）
├─ template/
│  └─ doc.html          文档页模板，构建时填入分类表
└─ public/              由 build_cf.py 生成
   ├─ index.html        文档页（/）
   ├─ _headers          分片的长缓存头
   ├─ browse/           分类浏览页；data.js 仅含元数据，items/{大类}.js 按需加载
   └─ data/
      ├─ p/{n}.json             诗库分片，每片约 120 KB
      └─ i/{大类}/{小类}.{k}.json  分类下标，每块 1000 条
```

`manifest.js` 里只有分类树和诗库分片的累计边界，所以 Worker 打包体积和分片数量无关。

## 路由

| 路径 | 内容 |
|---|---|
| `/` | 调用文档页（静态文件，不执行 Worker） |
| `/doc` | 同上，静态直出，无重定向 |
| `/api` | 分类总表 JSON |
| `/all` | 全库随机一首 |
| `/shanshui` | 大类随机（山水） |
| `/lushan` | 小类随机，无需父级 |
| `/shanshui,lushan` | 多选，逗号分隔，等概率各占一份 |
| `/line` | 全库随机连续两句 |
| `/line/songbie,jizeng` | 在指定分类内摘句 |
| `/browse/` | 可视化分类浏览（首屏小，分类数据按需加载） |
| `/data/*` | 语料分片，长缓存，供前端直接取用 |

分类全部平铺成一级路径，没有层级查询参数；写错的路径统一按「未知分类」返回 400 / 2002。
返回体前四个字段是 `content` / `origin` / `author` / `category`。

同一 IP 每 60 秒最多 60 次 API 请求（平均约 1 次/秒，允许短时突发），
超限返回 `429 / 1004` 与 `Retry-After: 60`；`OPTIONS` 预检不计数。
原生限流按 Cloudflare 机房分别近似计数，不保证跨机房的严格全局限额。

多个分类先等概率选分类，再在分类内选作品和句对；一次最多 20 个，未知分类返回 400 / 2002。
101 个 slug 全局唯一，路径全 ASCII。题材用全拼或核心词避开与意象分类重名：
山水田园 `/tianyuan`、爱情相思 `/xiangsi`、悼亡挽歌 `/wange`、哲理悟道 `/wudao`；
荔枝因与「励志」的 `lizhi` 重名，改用 `/lychee`。
摘句额外返回 `title` 和 `poem` 基本信息块（ID、诗题、作者、朝代、分部、体裁、分类、标签）。
摘句模式统一返回 JSON：即使写成 `.txt` 也返回 `application/json`；普通分类的 `.txt` 不受影响。

## 更新数据

```bash
python -m tagger.build            # 重建语料（改了规则或新增数据集时）
python tools/build_cf.py          # 重新分片（约 20 秒）
cd cloudflare && npx wrangler deploy
```

`build_cf.py` 采用确定性覆盖写入，不做批量删除；调整分片大小后旧文件可能留在磁盘，
但不会被新的 `manifest.js` 引用，因此不影响线上。最终以构建末尾的分片数自检为准。
修改 `POEM_CHUNK_BYTES`（默认 120 KB）或 `IDX_SHARD`（默认 1000）后重新构建即可，
`manifest.js` 与 Worker 逻辑都会自动适配。

## 注意事项

1. **slug 重名**：「励志」与「荔枝」的 slug 都是 `lizhi`，所以分类下标按大类分了目录
   （`i/rensheng/lizhi.*` 与 `i/shiwu/lychee.*`）。若两者同名，扁平命名会互相覆盖——这是本项目踩过的坑。
2. **`run_worker_first` 保持关闭**。默认的"静态资源优先"会让 `/`、`/doc`、`/browse/*`、`/data/*`
   由静态层直接命中，既不执行 Worker、不占每日请求额度，也自动获得 CDN 缓存；
   只有 `/api`、`/line`、`/shanshui`、`/lushan` 这类随机接口才会进入 Worker。
   文档页因此写成两份静态文件（`public/index.html` 与 `public/doc.html`），
   这样 `/doc` 直接命中、不会先 307 跳到 `/doc/`。
3. **免费额度**：10 万请求/天，只统计真正执行了 Worker 的请求。
   每次调用 2 个子请求（免费版上限 50），CPU 约 2–4 ms（免费版上限 10 ms）。
   静态页与分片不计次；随机接口无法被缓存缩短（请求必然先运行函数），
   真要把额度压下去，只能让客户端一次取多条（`?n=20`）或改为读取静态池。
4. **不要提交 `public/data`**。30 MB 的生成物不应进版本库，`.gitignore` 已排除；
   CI 部署时先跑 `build_cf.py`。
5. 全宋诗（26 万首）未纳入。若要开启，先在 `tagger/build.py` 的 `DATASETS` 加一条，
   重新构建后分片数会涨到约 900 个，仍在 20,000 文件限制内。

## 精度实测

分类质量不是靠感觉，有可复现的度量。两个口径，结论差很多，都要看：

### 口径一：人工标注基准（`tools/eval_theme.py`）

以唐诗三百首 / 宋词三百首的**人工 tags** 作金标准，取题旨无歧义的 195 首，
测 top-1 准确率。这是唯一有客观答案的集合。

| 轮次 | 准确率 | 主要改动 |
|---|---|---|
| 初始 | 70.4% | — |
| 第二轮 | 81.0% | 人工标签先验 1.15→1.9；「别业」不再触发「送别」 |
| 第三轮 | 82.5% | 标题命中按题材分权重（题画 2.4 / 悼亡 1.5 / 送别 1.0） |
| 第四轮 | **85.6%** | 区分「真离别」与「寄赠体裁」；闺阁与边塞泛词降权 |

分题材：咏史怀古 100%、边塞征战 100%、山水田园 100%、悼亡伤逝 100%、
羁旅思乡 96%、送别赠答 88%、闺怨宫怨 84%、咏物寄兴 83%、题画咏艺 83%；
偏弱的是爱情相思 54%、哲理悟道 50%（这两类本身与羁旅、山水大量重叠）。

### 口径二：全唐诗盲测

从全唐诗随机抽样、**剔除有旧标签的诗**、由人工逐首判定。两轮各 30–40 首：

| 轮次 | 命中 | 说明 |
|---|---|---|
| 修正前 | 23/40 = 57.5% | — |
| 修正后（配对复测） | 19/30 = 63.3% | 5 处变化全部改为正确，无回退 |

**两个口径差 20 多个百分点，原因是语料构成，不是规则退步。**
《唐诗三百首》是历代选家筛过的名篇，题材清晰；而全唐诗里大量是应制、干谒、
贺官、佛偈、乐府拟作、组诗残句——这些诗的"题材"是仪式性的，本就不属于 19 个类目中的任何一个。

因此：**分类接口适合做"大概率的分类浏览"，不适合当作学术级题材判定。**
当前已用混合策略把 195 首人工基准从 83.6% 提升到 87.2%；
更高精度仍需扩大人工金标准并逐类校准，不能只看小样本的单一分数。

### 口径三：规则 + 语义模型混合（当前生产）

`tools/llm_tag.py` 用完整正文、词牌提示、置信度和最短证据做 21 题材标注，
并按 UID 断点续跑。195 首人工基准上的同口径对比：

| 方法 | 准确率 | 说明 |
|---|---|---|
| 关键词规则 | 83.6% | 稳定、可解释，弱类边界较粗 |
| DeepSeek Flash | 76.4% | 快，语义边界较规则灵活 |
| DeepSeek v4-pro | 76.9% | 更慢，提升有限 |
| **混合策略** | **87.2%** | 高置信规则保留 + 弱类语义重判 + 低置信终审 |

混合策略只对经抽查验证的七类弱类使用模型结果（寄赠、节令、闲适、应制、佛道、悼亡、咏怀），
其余仍保留高置信规则，避免全量替换造成回退。

`theme_conf` 是最终采用来源的置信度；规则与模型来源不同，数值不宜直接横向比较。
接口不提供按置信度过滤的参数，调用方可自行读 `tags.theme_conf` 判断。

这四个题材改用全拼或核心词作 slug，保证与意象分类不重名、路径全 ASCII。

相对原 19 类做了三处调整：

1. **送别赠答拆成「送别」与「寄赠酬答」**——前者场景是离别，后者是往还唱和。
   混在一起时 2.2 万首诗互相串味，现在按标题的"送/别/饯"与"寄/赠/酬/答"分开。
2. **哲理悟道拆出「佛道禅颂」**——全唐诗里佛偈禅颂量极大（2,420 首），
   判法与老庄玄理完全不同，不应混为一谈。
3. **应制酬和更名「应制干谒」**——把贺官授职、干谒求荐一并收进来。

题材与意象分类并存，互不覆盖；`/t/` 前缀确保不会与意象 slug 撞车
（`aiqing` 既是意象小类也是题材）。
